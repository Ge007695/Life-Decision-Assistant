文档说明

本指导书是项目进入开发阶段后的唯一施工依据。它回答三个问题：要做哪些功能、每个功能怎么做、模块之间怎么连接。申报书回答"为什么做"，本文件回答"怎么做"。

本项目为个人项目，不设岗位分工。因此本文的写法是"一个人按什么顺序做"，而不是"谁负责哪块"。阅读方式：先通读一遍（约 40 分钟），之后按里程碑用到哪章翻哪章——做 M1 看第二、三、十章，写规则看第四、六章，做实验看第十一章。动手写代码前，必须先读完第三章"核心数据契约"，否则后面一定返工。

一、项目定位与目标

1.1 一句话定位

把"规则复杂、普通人懒得算"的日常问题，做成一句话结论加一份可执行清单。

1.2 解决的四个具体问题

场景用户原本的状态本项目的输出
出门看到"湿度 92%、南风 3 级"，不知道今天该不该晾衣服"今天适合晾晒，18:00 前收衣"
时间记不清下个假期还有几天、哪天要补班"距元旦还有 41 天，1 月 4 日周六补班"
花钱实习工资被扣了一笔，不知道为什么；分期"每期 0.6%"不知道真实成本"本月到手 3,840 元，年度汇算预计可退 260 元""真实年化 13.0%"
办事办证材料总漏，跑两趟材料清单加勾选进度

1.3 三条硬约束（任何设计决策不得突破）

  1. 不设后端。全部逻辑在浏览器执行，静态部署。唯一外部依赖是公开天气接口的历史与预报数据。
  2. 不采集用户数据。成绩、工资、家庭地址一概不入库，只存浏览器本地；代码库里不允许出现任何真实个人信息。
  3. 不使用需登录的校内数据。教务系统、校园网、校卡数据一律不碰，避免合规争议。

这三条不是技术偏好，是项目能安全结题的前提。有人提出"加个后端存数据吧"，直接引用本节否决。

1.4 验收口径

结题时以"能打开、能演示、有数据支撑"为准：

  • 一个可长期访问的网址，四个模块均可操作；
  • 三组实验有结果（准确率、算法对比、试用数据），写进结题报告；
  • 软件设计说明书一份，含架构图、数据契约、测试记录。

二、总体架构

2.1 分层结构

系统自上而下分四层，加一个贯穿的配置层：

层次目录职责允许依赖
视图层src/views/、src/modules/*/页面、交互、路由组件层、服务层、内核层
组件层src/components/可复用界面单元无（纯展示）
服务层src/services/取数、缓存、本地存储无
内核层src/core/规则计算，输出结论仅配置层
配置层public/data/权重、阈值、政策、文案无

依赖只允许自上而下。内核层不得 import 视图层、服务层、任何 UI 库，也不得发起网络请求。这条规则看起来苛刻，但它换来一个关键能力：回测脚本可以在 Node 里直接调用同一份规则代码，保证"线上跑的模型"和"报告里评的模型"是同一个东西。一旦内核层耦合了界面，回测只能另写一套，两边结果必然对不上，评审一问就露馅。

2.2 目录结构

decision-assistant/

2.3 技术选型

项选择理由
前端框架Vue 3 + Vite组件化清晰，学习成本低，组内前端开发者已熟悉
状态管理不需要 Pinia，用 reactive + localStorage单页应用状态简单，引入状态库是过度设计
图表ECharts中文文档全，时间序列与对比图开箱即用
样式手写 CSS 变量 + 少量工具类避免引入 UI 库导致包体过大、风格不统一
回测Python 3 + pandas + numpy历史数据处理方便；通过子进程调用 Node 复用内核规则
部署GitHub Pages 或 Vercel 静态托管免费、长期可访问、支持自定义域名

为什么回测要调 Node 而不是 Python 重写规则：规则只有一份实现，回测通过 node scripts/backtest/run_rule.js <rule> <input.json> 调用内核，Python 只负责数据清洗、批量调用与统计。这样"回测的模型"与"线上的模型"严格一致。如果 Python 另写一套，两边迟早分叉。

2.4 部署流程

  1. 推到 GitHub 仓库，npm run build 产出 dist/；
  2. Vercel 关联仓库，自动构建，得到形如 https://xxx.vercel.app 的链接；
  3. 把链接写进 README、中期材料、结题报告，确保中期与结题时均可打开；
  4. 不要把预览用的临时隧道地址当作交付链接。

三、核心数据契约

这一章是全项目的"接口标准"。模块之间不直接互相调用业务逻辑，一律通过本章定义的三类结构通信。

3.1 统一结论对象 DecisionResult

所有规则函数的返回值必须符合这个结构。视图层只认这个结构，因此新增指数不需要改页面。

{
  "id": "drying",
  "version": "1.0.0",
  "level": 3,
  "levelLabel": "适宜",
  "score": 82,
  "headline": "今天适合晾晒，18:00 前收衣",
  "actions": ["09:00—11:00 晾出", "18:00 前收回"],
  "evidence": [
    { "label": "相对湿度", "value": "68%", "weight": 0.30, "contribution": 0.22 },
    { "label": "风速", "value": "3.1 m/s", "weight": 0.20, "contribution": 0.16 }
  ],
  "configRef": "indices.json#drying",
  "updatedAt": "2026-11-02T09:00:00+08:00"
}

字段含义：

字段类型说明
idstring规则唯一标识，与 indices.json 的键一致
versionstring规则版本，回测报告必须写清楚用的是哪一版
level0—4 整数语义等级，0 为最差、4 为最佳
score0—100连续得分，用于排序和时间窗比较
headlinestring一句话结论，来自配置的文案模板
actionsstring 数组可执行动作，渲染成勾选清单
evidence对象数组判定依据，用于解释"为什么这么判"
configRefstring指向配置节点，便于排查

evidence 不是装饰。答辩时被问"凭什么说今天适合晾衣服"，把它投出来就是答案；回测时它也用来定位误判原因。

3.2 指数配置 Schema

所有阈值、权重、文案放在 public/data/indices.json，代码里不允许出现未命名的数字。

{
  "meta": { "version": "1.0.0", "updated": "2026-11-01" },
  "indices": {
    "drying": {
      "label": "晾晒指数",
      "inputs": ["temp", "humidity", "windSpeed", "precipProb", "solar"],
      "weights": {
        "temp": 0.20, "humidity": 0.30, "windSpeed": 0.20,
        "precipProb": 0.25, "solar": 0.05
      },
      "normalize": {
        "temp": [10, 32],
        "humidity": [90, 40],
        "windSpeed": [0, 5],
        "precipProb": [80, 0],
        "solar": [0, 800]
      },
      "levels": [
        { "min": 80, "level": 4, "label": "适宜", "headline": "今天适合晾晒，{bestWindow} 前收衣" },
        { "min": 60, "level": 3, "label": "一般", "headline": "可以晾，但干得慢，建议延长晾晒时间" },
        { "min": 40, "level": 2, "label": "较差", "headline": "不建议晾晒，改为室内除湿" },
        { "min": 0, "level": 1, "label": "不宜", "headline": "今天晾不干，改用烘干或推迟" }
      ]
    }
  }
}

关键设计：normalize 的区间写成 [劣端, 优端]，而不是 [min, max]。这样"湿度越低越好、风速越大越好"这类方向相反的指标可以用同一套归一化函数处理，引擎不必为每个指标写分支。归一化公式：

score = clamp((value − poor) / (good − poor), 0, 1)

headline 里的 {bestWindow} 这类占位符由引擎在拼装阶段替换，规则函数不拼字符串。

3.3 政策配置 Schema

节假日与税率属于外部规则，会变。做法是配置文件加版本号，页面显示依据。

holidays.json：

{
  "meta": { "year": 2027, "source": "国务院办公厅关于 2027 年部分节假日安排的通知", "status": "pending" },
  "holidays": [
    { "name": "元旦", "start": "2027-01-01", "end": "2027-01-03" }
  ],
  "makeupWorkdays": ["2027-01-09"],
  "schoolTerms": [
    { "name": "寒假", "start": "2027-01-18", "end": "2027-02-28" }
  ]
}

status 为 pending 时，页面显示"2027 年安排待公布"，并保留手工录入入口。这一点很实际：每年安排通常在 11 至 12 月才发布，程序必须能优雅地处理"还没有数据"这个状态，不能白屏或报错。

tax-rules.json：

{
  "meta": { "version": "2019-01-01", "source": "国家税务总局关于全面实施新个人所得税法若干征管衔接问题的公告", "note": "政策调整时以官方最新公告为准" },
  "serviceIncome": {
    "threshold": 4000,
    "deduction": { "flat": 800, "rate": 0.20 },
    "brackets": [
      { "upper": 20000, "rate": 0.20, "quickDeduction": 0 },
      { "upper": 50000, "rate": 0.30, "quickDeduction": 2000 },
      { "upper": null, "rate": 0.40, "quickDeduction": 7000 }
    ]
  }
}

税率表必须可配。实现时以国家税务总局最新公告为准，不要凭记忆写死数字；每期政策更新只改这个文件。

3.4 本地状态 Schema

storage.js 统一封装，键名固定前缀 lda:：

键内容说明
lda:settings城市、室内温度、体感偏移体感校准写这里
lda:salary最近一次工资测算输入只存输入，不存身份证等敏感信息
lda:checklist办事清单勾选进度按清单 id 分组
lda:feedback体感反馈记录（日期 + 偏冷/偏热）用于校准，最多保留 90 条

写入前做一次 try/catch，隐私模式下 localStorage 可能不可用，失败时降级为内存态并提示"本次记录不会保存"。

3.5 数据流总图

一次"打开首页"的完整链路：

用户打开首页
   ↓
视图层 Home.vue 请求结论
   ↓
服务层 weather.js 读缓存（24 小时有效）
   ├─ 缓存有效：直接返回
   ├─ 已过期：调用天气接口
   └─ 调用失败：沿用上次缓存并标注"数据可能过期"
   ↓
内核层 engine.runBatch(ids, weatherInput, config)
   ↓
每个规则函数计算，返回 DecisionResult 数组
   ↓
视图层渲染：最高优先级结论做横幅，其余做指数条

规则函数内部不取数、不读存储、不碰 DOM，只接受入参、返回结论。这条纪律由代码评审保证：src/core/ 下出现 fetch、window、document、localStorage 一律打回。

4.2 天气数据接入

接口选用免费额度的公开气象服务（如和风天气、Open-Meteo）。接入要点：

  1. 按日缓存：每日首次打开才请求，结果存 localStorage 24 小时，避免刷新即调用导致额度耗尽；
  2. 失败降级：请求失败读上次缓存，页面上标注"数据更新于 X 小时前"；无缓存则展示占位并提示稍后重试；
  3. 密钥外置：接口密钥放 .env.local，不进仓库；前端直连的密钥要限制域名白名单；
  4. 字段映射：接口字段名与内部 weatherInput 做一层适配，接口换了只改适配层。

内部统一的数据结构：

{
  "city": "深圳",
  "date": "2026-11-02",
  "hourly": [
    { "time": "09:00", "temp": 24.1, "humidity": 68, "windSpeed": 3.1, "windDir": "SE", "precipProb": 10, "solar": 520 }
  ],
  "daily": { "tempMin": 20, "tempMax": 27, "sunrise": "06:32", "sunset": "17:48" }
}

4.3 算法说明

露点温度（Magnus 公式），实现在 src/core/utils/dewpoint.js：

α = ln(RH / 100) + a·T / (b + T)
Td = b·α / (a − α)
其中 a = 17.27，b = 237.7，T 为摄氏温度

返潮判定（三条同时满足才预警），实现在 rules/damp.js：

条件阈值说明
露点接近室内表面温度Td ≥ Ti − 1Ti 默认 22 ℃，可在设置页修改；无实测值时用过去 72 小时最低气温近似
持续高湿相对湿度 ≥ 85% 连续 6 小时以上短时高湿不算
风向偏南风（SE/S/SW）且风速 ≥ 2 m/s回南天的水汽来源

这里的 Ti 是简化假设，报告里必须写明"室内表面温度采用近似值，未实测"，这是诚实的实验边界，不要含糊过去。

最佳晾晒时间窗，实现在 rules/drying.js 的 bestWindow()：

  1. 取未来 24 小时逐小时数据；
  2. 对每个 2 小时滑动窗口计算平均晾晒分；
  3. 取最高分窗口；若最高分低于 60，返回"全天不建议"，不硬给时间。

体感温度参照 Steadman 简化式，实现在 utils/apparent-temp.js：

e  = RH / 100 × 6.105 × exp(17.27T / (237.7 + T))
AT = T + 0.33e − 0.70ws − 4.00

穿衣映射由 clothing-table.json 决定，例如体感 26 ℃ 以上输出"短袖 + 短裤/薄长裤"，18—25 ℃ 输出"短袖 + 薄外套"，10—17 ℃ 输出"长袖 + 外套"，不要用 if-else 写死在代码里。

4.4 页面结构

首页自上而下：结论横幅、指数条组（每项可展开看依据）、出门清单、最佳时间窗图、7 天简表。一屏之内必须看完前两块，滚动才看到其余内容。

4.5 验收标准

  • 断网时页面不崩，显示上次数据并标注时间；
  • 手工把配置里 drying 的权重改成 0.5，页面结论随之变化（证明配置生效）；
  • 结论卡"依据"能展开，显示每项指标的权重与贡献。

T-3调休提醒列出本年度所有调休上班日P0
T-4学期节点距寒暑假还有几天，开学/放假日期P1
T-5假期出行准备清单结合天气模块生成P1

5.2 实现要点

倒计时用本地日期做差，不做时区换算（用户只在本机看）。日历按"数据驱动"渲染：把 holidays.json 展开成 {date: type} 的字典，渲染时查表，不在模板里写判断逻辑。

holidayCountdown() 的返回也要符合 DecisionResult：headline 为"距元旦还有 41 天"，actions 为"1 月 4 日（周六）需补班"这类提醒。这样时间模块不需要自己的展示组件，直接复用 DecisionCard。

5.3 验收标准

  • 切换年份后，无数据的年份显示"待公布"而不是报错；
  • 手工往 makeupWorkdays 加一天，日历立即显示为灰色补班日。

六、模块三：花钱决策

6.1 功能清单

编号功能说明优先级
M-1实习到手工资测算输入日薪/月薪与工作日 → 预扣税、到手金额P0
M-2计税口径对比劳务报酬与工资薪金两种口径的到手差异P1
M-3年度汇算提示按年度税率表重算，给出多退少补的估算P1
M-4分期真实年化输入本金、期数、每期费率 → IRRP0
M-5方案对比多组分期方案并排比较P1
M-6算法对比实验三种 IRR 算法的迭代次数与精度P1

6.2 工资测算

计算顺序：收入 → 扣除额 → 应纳税所得额 → 查预扣率表 → 预扣税额 → 到手金额。所有参数从 tax-rules.json 读取，代码里只保留公式。

if (income <= threshold)  taxable = income − deduction.flat
else                      taxable = income × (1 − deduction.rate)
tax = taxable × rate − quickDeduction
takeHome = income − tax

年度汇算部分要写清楚这是估算：把全年劳务报酬并入综合所得，减去基本减除费用六万元与专项附加扣除后按年度税率表重算。页面上必须标注"本结果为估算，实际以税务部门年度汇算为准"，不要给出确定性口吻。

6.3 分期真实年化

现金流构造：期初收入本金 +P，此后每期支出 −(P/n + P×feeRate)。求解：

NPV(r) = P − Σ_{t=1..n} (P/n + P×feeRate) / (1+r)^t = 0

三种算法实现在 utils/irr.js：

方法做法记录指标
二分法区间 [−0.99, 10]，按 NPV 符号二分，直到 |NPV| < 1e-8 或 200 次迭代次数、最终误差
牛顿法r ← r − NPV(r)/NPV'(r)，初值 0.01迭代次数、是否发散
扫描插值步长 0.001 扫描符号变化点，再线性插值扫描点数、精度

必须处理的边界：无符号变化（无解）、多解（现金流方向多次改变）、n 过大导致浮点误差积累。无解时返回明确提示，不要返回 NaN 让页面显示"年化 NaN%"。

6.4 验收标准

  • 输入"本金 6000 元、12 期、每期费率 0.6%"，页面显示的真实年化明显高于 7.2% 的名义值；
  • 三种算法结果差值小于 0.01 个百分点，但迭代次数不同（这就是实验要的对比数据）；
  • 输入非法值（0 期、负本金）有友好提示，不报错。

七、模块四：办事清单（可选）

内容型模块，价值在于准确，不在于技术。checklists.json 存事项、材料、办理地点、时限，页面做勾选与进度。

必须遵守一条：每条清单标注"信息采集日期"与"以官方最新公告为准"。政策变动导致的信息过时，是这个模块最大的风险，标注是唯一的免责方式。若时间紧张，本模块整体砍掉，不影响项目完整性。

十、单人开发的自我管理

本项目是个人项目，没有分工，所有角色由一人轮流扮演。这一章不写"谁做什么"，只写一个人怎么不把自己搞乱——单人开发最大的风险不在工作量，而在没有人拦着你把架构改坏。

10.1 一人五顶帽子

同一时间只戴一顶帽子，切换角色前先提交代码。最常见的失败情形是"写页面时觉得数据结构不顺，顺手把内核层改了"，结果首页没做完、规则也没测过。

角色主要工作时间占比
架构与内核数据契约、引擎调度、src/core/ 规则与工具函数约 40%
前端实现页面、五个共享组件、路由与样式约 35%
配置与内容三份 JSON、政策校核与版本标注、文案约 10%
测试与实验单元用例、回测脚本、试用组织约 10%
文档与结题设计说明书、报告、演示视频约 5%（后期集中）

10.2 替代"协作"的五条自我约束

  1. 接口先定后写：改动 DecisionResult 或任一配置 Schema，先改本文档第三章，再改代码，改完在文末"变更记录"写一行日期和原因。只改代码不改文档，两周后自己都不记得当初为什么这么定。
  2. 内核层纪律交给工具守：在 ESLint 里对 src/core/** 配 no-restricted-globals，禁掉 fetch、window、document、localStorage，提交前跑一次。一个人的代码没人复核，"我记得不在这里写网络请求"是靠不住的，机器拦才有效。
  3. 每周日 20 分钟自检：对着第九章里程碑逐条打勾——本周产出是什么、下周做什么、卡在哪。连续两周没有可演示的进展，就砍掉一个 P2 功能，不要硬撑。
  4. 分支从简，但要留退路：一个人不需要 feat/ 分支，直接提交 main；但每个里程碑完成时打一个 tag（m1、m2……）推到远端。出问题能退回去，结题时这份 tag 记录本身就是进度证明。
  5. 每月找一双外部眼睛：代码不必请人复核，但结论必须被外部检验——每月请导师或同学打开网站点三分钟，只问一句"你看得懂这行结论吗"，记下他卡在哪一步。自己用久了会习惯所有别扭的地方，这是低成本发现交互问题的唯一办法。

十一、测试方案

11.1 单元测试

每个规则函数至少三个用例：典型值、边界值、异常值。以晾晒为例：

用例输入要点期望
典型晴好湿度 60%、风速 3、降水概率 10%等级 4，结论含时间窗
边界高湿湿度 84%、其余晴好等级 3，不出现"适宜"
异常湿度过期缺失返回降级结论，不抛异常

11.2 配置校验

启动时校验三份 JSON：必填字段存在、权重之和为 1（允许 ±0.01 误差）、normalize 区间两端不相等。校验失败直接在页面顶部提示"配置异常"，不要静默降级，否则错误会藏到演示当天。

11.3 回测

  1. fetch_history.py 拉取深圳近两年逐小时数据，落 scripts/backtest/data/；
  2. backtest_indices.py 逐日构造输入，调用 Node 跑规则，把 DecisionResult 存成 CSV；
  3. 与实测结果比对：晾晒预测"适宜"的次日，若实际降水 > 0 或次日湿度仍 > 85%，记误判；
  4. 输出准确率、召回率、混淆矩阵，以及三套权重方案（经验权重、等权、拟合权重）的对比表。

11.4 可用性测试

找 20 名同学，给三个任务（判断今天能否晾衣、查下个假期、算实习到手工资），记录完成率与用时，再用五级量表问"结论是否可信"。这部分数据是报告里最好写的部分，成本也最低。

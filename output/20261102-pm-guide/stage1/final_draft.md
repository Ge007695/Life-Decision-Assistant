# 生活决策助手项目管理指导标准

**项目全称**：面向日常决策的规则引擎设计与实现——以深圳生活场景为例

**文档版本**：v1.0　**编写日期**：2026 年 11 月 2 日　**维护人**：葛孝语

**适用对象**：项目负责人（个人项目，全部开发由一人承担）

## 文档说明

这份文件规定本项目在开发过程中如何使用版本管理工具完成三件事：把代码传到远端仓库、把不同来源的改动合到一起、在出问题时退回到任何一个历史状态。它不讨论"要不要用 Git"——这是必须的；它只规定"具体怎么用"，并且给出可以直接复制的命令。

三个概念在本文件中的统一叫法：上传指把本地提交推送到远端仓库（commit 加 push）；合并指把两条不同的历史线并到一起，或把远端更新并入本地；回溯指让工作区、某个文件或整个仓库回到过去某个状态（restore、reset、revert、reflog）。

本文件同时是一份自查依据。第十章给了四张检查清单，权重从"每次提交"到"结题之前"逐级提高。任何一步没做到，责任在项目负责人本人，因为没有第二个人可以推。

## 一、为什么一个人也要做版本管理

### 1.1 三个必须满足的硬要求

单人项目做版本管理，不是为了协作，而是为了应对三个具体场景，缺一个都不行。

**可回溯：改坏了要能退回去。** 一个人在重构时最容易犯的错是"改到一半发现方向错了，但已经改了三十个文件"，没有版本管理就只能凭记忆一个个改回来，通常改不干净，最后留下半新半旧的代码。有了提交点，退回上一个可用状态只需要一条命令。

**可交付：结题材料要能证明过程。** 学校结题与可能的中期检查，看的不只是最终成果，还包括"这一年到底做了没有"。仓库的提交记录、里程碑标签、每个阶段的代码差异，是最难伪造、也最省口舌的过程证据。等到 2027 年 8 月才回头补过程材料，是补不出来的。

**可恢复：硬盘坏了不能全丢。** 代码、配置、文档、回测脚本全在一台笔记本上，一次进水、一次误删、一次系统重装就归零。远端仓库是唯一的异地副本，这也是本文件要求"每天至少推送一次"的根本原因。

### 1.2 四条基本原则

1. **一切进仓库**：代码、配置 JSON、设计文档、回测脚本、进度周志、演示稿源文件，全部纳入版本管理。只有密钥、依赖包、大体积数据在外。判断标准是"丢了会不会心疼"，会心疼就进仓库。
2. **小步提交**：一次提交只做一件事，改完能跑就提交。宁可一天提交六次，不要一周提交一次然后写一句"更新"。
3. **主线可运行**：`main` 分支在任何时刻都必须能跑起来、能部署。因为网站托管绑定的是 `main`，推上去就等于发布到线上，主线坏了等于线上挂着 404。
4. **能退才敢改**：动手大改之前先打标签或开分支。有了退路，重构就从"冒险"变成"试验"，这是个人开发效率差距最大的地方。

### 1.3 与本项目文档体系的关系

本文件是《生活决策助手项目工作指导书》的配套规程。工作指导书规定"做什么功能、模块怎么连"，本文件规定"代码怎么管、版本怎么留"。两者冲突时以工作指导书的功能定义为准，以本文件的操作流程为准。

## 二、仓库初始化

### 2.1 仓库怎么划分

只建一个仓库，代码与文档同仓。理由是单人项目里文档和代码的版本必须对应——结题时要说清"v0.9 版本的晾晒指数权重是多少"，只有同仓才能一条命令查出来。文档另建仓库的唯一好处是瘦身，本项目代码量远达不到需要瘦身的程度。

仓库名建议 `decision-assistant`，本地路径放在非系统盘、路径不含空格和中文的位置，例如 `D:/code/decision-assistant`。放在桌面或中文路径下会带来两个麻烦：部分工具链对非 ASCII 路径处理不稳定；备份时容易和临时文件混在一起。

### 2.2 目录约定

```
decision-assistant/
├── public/data/            配置层：指数、假期、税率、穿衣表
├── src/core/               内核层：引擎、规则、纯函数工具
├── src/services/           服务层：天气取数、缓存、本地存储
├── src/components/         组件层：五个复用组件
├── src/modules/            业务模块：出门 / 时间 / 花钱 / 办事
├── src/views/              首页与设置页
├── scripts/backtest/       回测脚本（Python）
├── docs/                   设计说明书、测试记录
│   ├── progress/           周志与阶段截图
│   └── decisions/          关键技术决策记录
├── .gitignore
├── .gitattributes
├── README.md
└── CHANGELOG.md
```

`docs/decisions/` 这个目录单人项目里最容易被省掉，但它恰恰最有用：凡是"为什么这么定"的问题（为什么用加权评分而不是规则树、为什么回测用两年数据），写一条三五百字的短记录。三个月后自己会忘，结题答辩时也会被问。

### 2.3 初始化命令序列

以下命令按顺序执行，一次完成。

```
cd D:/code
mkdir decision-assistant && cd decision-assistant
git init -b main
git config user.name "葛孝语"
git config user.email "你的邮箱"
git config core.autocrlf false
git config pull.rebase true
```

`git init -b main` 直接把默认分支定成 `main`，避免出现 `master` 与 `main` 并存。`core.autocrlf false` 配 `.gitattributes` 统一换行符，防止跨编辑器改动被识别成"整个文件都改了"。`pull.rebase true` 让拉取默认用变基方式，历史线保持一条直线，详见第六章。

初始化后立刻做第一次提交，提交内容只有三样：`.gitignore`、`.gitattributes`、`README.md`。不要等到写了代码再提交，第一次提交是仓库的锚点。

### 2.4 .gitignore 模板

直接复制下面内容，本项目暂时用不到的也一并写上，省得以后补。

```
# 依赖
node_modules/
.pnpm-store/

# 构建产物
dist/
build/
*.local

# 环境与密钥
.env
.env.*
!.env.example

# 数据与缓存
scripts/backtest/data/
scripts/backtest/output/
*.csv
*.parquet

# 编辑器与系统
.vscode/
.idea/
.DS_Store
Thumbs.db

# 日志与临时文件
*.log
npm-debug.log*
~$*
```

`~$*` 这一行专门排除 Office 与 WPS 打开文档时生成的锁文件，这类文件会反复出现在工作区，看着极烦，提交上去还会互相覆盖。

`*.csv` 全局排除是个刻意的选择：回测数据、导出的中间结果都很大，进仓库会让克隆变慢、推送变慢。数据本身放到第八章的归档方案里管理，仓库只记录"数据从哪来、校验值是多少"。

### 2.5 .gitattributes

一句话就够，作用是强制仓库内统一 LF 换行、并把常见二进制标记为二进制，避免 Git 试图做文本 diff。

```
* text=auto eol=lf
*.png binary
*.jpg binary
*.pdf binary
*.docx binary
*.xlsx binary
*.mp4 binary
```

### 2.6 远程仓库与首次推送

远端选 GitHub 私有仓库即可，个人项目不需要公开；如果国内网络推送不稳定，用 Gitee 或学校可用的 CNB 也可以，三者命令完全一致。建好空仓库后绑定远端。

```
git remote add origin git@github.com:你的账号/decision-assistant.git
git push -u origin main
```

`-u` 只需第一次，作用是记住上游分支，之后直接 `git push` 就行。SSH 方式需要先在本地生成密钥并把公钥贴到账号设置里；不想配 SSH 就用 HTTPS 加个人访问令牌，令牌只输入一次，让凭据管理器记住。

推送这一步如果卡住不动，先查本机代理：命令行里存在 `http_proxy` 或 `https_proxy` 环境变量时，Git 会走代理，而代理没开或端口不对就表现为长时间无响应。临时关闭可以用 `git config --local http.proxy ""` 覆盖，需要代理时再设为本地代理地址。

## 三、分支与版本号

### 3.1 主线策略

单人项目只用一条长期分支：`main`。所有日常开发直接在 `main` 上提交，不为了"看起来规范"而给每个功能开分支——一个人开分支再合并，等于自己给自己增加一道没有价值的手续，实际结果是分支开了忘记合，最后在三个分支之间来回找代码。

但 `main` 有两条不可破的规矩：提交前能本地跑通；推送前先拉取。原因很直接，网站的自动部署绑定 `main`，推一次就上线一次，主线坏了线上就挂了，而这是中期演示时最尴尬的事故。

### 3.2 什么时候才需要开分支

只有三种情形值得开分支，另外的情形一律在 `main` 上做。

1. **大范围重构**：要动内核层的目录结构或改动 `DecisionResult` 的字段，预计两天以上。这种改动中途一定不可用，必须隔离，改完验证通过再合并。
2. **两套方案对比**：例如 IRR 的牛顿法和二分法要分别实现并跑基准测试，或者两套指数权重方案要并行回测。这时两个分支各自能跑，比在一个分支里注释来注释去清楚得多。
3. **追一个难查的缺陷**：在主干上直接试会污染主线，开 `fix/` 分支，找到原因再带回。

分支命名统一为 `feat/模块名`、`exp/方案名`、`fix/问题简述`，全小写、用连字符。`exp/` 这类分支允许失败，验证完把结论写进 `docs/decisions/` 后删掉，代码不必合回主干——记录结论比保留代码更有价值。

### 3.3 分支的完整生命周期

```
git switch -c exp/irr-newton        从主干切出实验分支
git switch main                     回到主干继续日常开发
git merge --no-ff exp/irr-newton    验证通过后合并，保留分支痕迹
git branch -d exp/irr-newton        合并后删除本地分支
git push origin --delete exp/irr-newton   同步删除远端分支
```

一次合并就完成闭环：切出、验证、合回、清理。留下没合也没删的分支是最常见的坏习惯，一个月后自己都分不清哪个是活的。

### 3.4 里程碑标签与版本号

标签是本项目的骨架。第九章的里程碑 M1 到 M8 各对应一个标签，标签名与里程碑编号一致，附注写清完成判据，这样任何时刻都能精确回到"M3 完成时"的状态。

```
git tag -a m1 -m "M1 骨架：命令行可输出 DecisionResult"
git tag -a m3 -m "M3 出门模块完整：四类指数上线，断网可降级"
git push origin --tags
```

对外交付与演示用语义化版本号，`v0.1` 到 `v1.0`，与标签并存但用途不同：标签记录内部进度，版本号记录可以拿给别人看的状态。建议对照关系如下。

| 版本号 | 对应里程碑 | 状态说明 |
|--------|------------|----------|
| v0.1 | M1 骨架 | 仅命令行可运行，无界面 |
| v0.3 | M2 首页 | 首页可演示，只有晾晒一条规则 |
| v0.5 | M3 出门完整 | 四类指数上线，中期可用 |
| v0.7 | M5 花钱模块 | 四模块齐全，开始做实验 |
| v0.9 | M7 实验 | 回测与试用数据完成，进入文档阶段 |
| v1.0 | M8 结题 | 交付版本，冻结代码 |

版本号一旦打到 `v1.0` 并用于结题提交，代码就不再改动。结题之后如需继续开发，开 `v1.1` 走后续版本，不要把已经提交给学校的版本改掉。

### 3.5 发布与线上版本的对应

网站托管（Vercel 或 GitHub Pages）绑定 `main` 后，每次推送会自动构建部署。这带来一个必须建立的意识：**线上版本永远等于 `main` 的最新提交**。因此中期演示、结题答辩这类有明确时间的场合，演示前一天不要再往 `main` 推未验证的改动；确需改动就开分支，验证通过后再合回，并留出至少半天时间确认线上正常。

## 四、提交规范

### 4.1 一次提交只做一件事

判断标准很简单：能不能用一句不含"和"的话描述这次提交。能，就算一件事；不能，就拆开。常见错误是把"加了返潮规则、顺便改了首页配色、又更新了 README"合成一次提交，出问题时无法只回退其中一项。

提交的时机是"一个可运行的小状态达成"，不是"一天结束"。中途跑不通的代码不要提交，用暂存区（stash）挂起来，见 7.3 节。

### 4.2 提交信息格式

统一用下面的结构，第一行不超过 50 个字符，需要解释时空一行再写正文。

```
<类型>(<范围>): <一句话说明>

<为什么这么改，可省略>

<关联的里程碑或问题，可省略>
```

类型只有七种，够用且必须严格。

| 类型 | 用于 | 示例 |
|------|------|------|
| feat | 新增功能 | feat(drying): 增加晾晒指数时间窗推荐 |
| fix | 修缺陷 | fix(weather): 缓存过期后未刷新导致结论不变 |
| refactor | 不改行为地重构 | refactor(core): 规则函数改为统一返回 DecisionResult |
| docs | 文档 | docs(decisions): 记录返潮判定为何取室内温度近似值 |
| test | 测试 | test(irr): 补二分法与牛顿法的边界用例 |
| data | 配置与数据 | data(indices): 按回测结果调整晾晒权重 |
| chore | 杂务 | chore: 增加 ESLint 内核层限制规则 |

范围用模块名或目录名，小写，不用中文。类型和范围都用英文的好处是以后可以用命令筛选，例如 `git log --oneline --grep="fix(drying)"` 一次列出所有晾晒相关的修补。

### 4.3 五个真实示例

```
feat(core): 实现规则调度与批量执行
feat(revert): 新增回南天预警三条判定条件
fix(backtest): 修复逐日回算误用次日数据的问题
docs(decisions): 说明为何选加权评分而非规则树
chore(lint): 禁止 core 目录出现 fetch 与 localStorage
```

四条都具体到"改了什么"，没有任何一条是"更新代码"或"修改"。

### 4.4 提交前自检三问

1. **能跑吗**：本地起服务，页面能打开，改动的那个规则输出正常。做不到就先 stash，不要提交。
2. **只做了一件事吗**：`git diff --staged` 看一遍，出现无关文件就撤出暂存区。
3. **有不该进去的东西吗**：密钥、`.env`、数据文件、`node_modules`、Office 锁文件。用 `git status` 逐个确认，不要用 `git add .` 一把梭。

### 4.5 绝对不进仓库的内容

- 任何密钥、令牌、私人邮箱密码，包括写在注释里的。密钥一旦推送，即使后来删除，历史里仍然存在，必须视为已泄露并更换。
- 大体积原始数据与视频。GitHub 单文件上限 100MB，超过直接拒绝推送；50MB 以上就会拖慢所有操作。
- 依赖目录与构建产物。它们可由 `npm install` 与构建命令重新生成。
- 别人的代码。参考的例程可以读、可以改写，但整段复制进仓库要注明出处，答辩被问到时说不清来源最麻烦。

## 五、上传：从改动到远端

### 5.1 日常六步

每天至少走一遍，全程不超过两分钟。

```
git status                  看有哪些改动，确认没有多余文件
git diff                    看具体改了什么，避免把调试代码带上去
git add -p src/core/        逐块确认后暂存，比 git add . 安全
git commit -m "feat(drying): 增加时间窗推荐"
git pull --rebase           先并入远端更新，防止推送被拒
git push                    推到远端
```

`git add -p` 是单人项目里最值得养成的习惯：它会逐块问"这段要不要提交"，可以顺手把调试用的 `console.log` 留在工作区而不进这次提交。

### 5.2 三种推送失败与处理

| 报错关键字 | 含义 | 处理 |
|------------|------|------|
| `non-fast-forward` 或 `rejected` | 远端有本地没有的提交 | 先 `git pull --rebase`，解决可能的冲突后再推送 |
| `File ... is 105.00 MB; exceeds GitHub's limit` | 单文件超限 | 从提交中移除并加入 `.gitignore`；已提交则用 `git rm --cached` 撤出后重做该提交 |
| `Authentication failed` 或 `Permission denied (publickey)` | 凭据或密钥问题 | HTTPS 重新输入令牌；SSH 用 `ssh -T git@github.com` 测试并重新添加公钥 |

第三种情况还有一个隐蔽原因：远端仓库地址写成了别人的或已改名。用 `git remote -v` 看一眼就能确认。

### 5.3 上传频率的底线

不低于每天一次，且必须在当天工作结束前完成。理由不是强迫症，而是"未推送的提交只存在于本机磁盘"，硬盘故障时和没提交没有区别。周末或考试周完全不写代码时，也要确认最后一次提交已经推上去。

### 5.4 数据与成果文件的上传边界

回测数据、演示视频、结题 PDF 这类文件不放进代码仓库，改用两种方式：小于 20MB 的放 GitHub Releases，随标签附上；更大的放网盘，仓库里只放一个 `docs/data-source.md` 记录文件名、来源、获取日期和 SHA256 校验值。这样既保证仓库轻量，又保证任何人拿到仓库能追溯数据。

## 六、合并：把两条历史并到一起

### 6.1 单人场景下的合并是什么

单人项目的合并只有两种情况：一是把远端更新并入本地（换电脑写、在网页上改过文件、或者另一台设备推过），二是把实验分支合回主干。前者几乎每天都发生，后者一个月一两次。真正需要手工解决冲突的场合很少，但必须会。

### 6.2 拉取用变基还是合并

本项目统一用 `git pull --rebase`，理由是这样历史是一条直线，`git log` 读起来就是"按时间发生的事"，找某次改动不需要在交叉的合并线里翻。区别如下。

| 方式 | 结果 | 适用 |
|------|------|------|
| `git pull --rebase` | 本地提交被"挪"到远端提交之后，历史线性 | 单人项目的日常拉取，默认用这个 |
| `git pull`（默认 merge） | 生成一个合并提交，历史出现分叉 | 多人协作、需要保留并行开发痕迹时 |

`pull.rebase true` 已在初始化时设好，所以直接 `git pull` 就是变基。

### 6.3 冲突处理四步

变基或合并时出现 `CONFLICT` 不要慌，冲突只发生在同一个文件的同一段被两边改过的地方，范围通常很小。

1. **看清单**：`git status` 会列出 `both modified` 的文件，只处理这些。
2. **改文件**：打开文件，搜索冲突标记——Git 会插入由连续小于号、等号、大于号组成的三行标记，把同一处代码切成三段：当前分支的、分隔线、另一边的。保留需要的部分，删掉全部标记行。
3. **标解决**：`git add 文件名`，逐个标记。全部处理完用 `git status` 确认没有遗留的未合并文件。
4. **继续或放弃**：变基中用 `git rebase --continue`，合并中用 `git commit`；判断改错了就用 `git rebase --abort` 或 `git merge --abort` 整体回到操作前，回到干净状态重新来。

冲突解决后必须本地跑一次，确认不是"标记删干净了但逻辑拼坏了"。这一步最容易跳过，也最容易把三天后的自己坑住。

### 6.4 分支合回主干

实验分支验证通过后合回 `main`，用 `--no-ff` 强制生成一个合并提交。

```
git switch main
git merge --no-ff exp/irr-newton -m "merge: 采纳牛顿法作为 IRR 默认实现"
```

保留合并提交的价值在于：结题时能一眼看出"这一整块是并行试验后并入的"，而不是散在几十个零碎提交里。如果分支做的是废弃方案，不要合并，直接写决策记录然后删分支。

### 6.5 三条禁令

1. **不向 `main` 强推**。`git push -f` 会覆盖远端历史，一旦远端有你本地没有的提交就直接丢失，且无法从远端恢复。只在自己独占的实验分支上允许强推。
2. **不重写已推送的历史**。对已推送的提交做 `rebase` 或 `commit --amend` 会造成本地与远端分叉，只能用强推解决，踩进第 1 条。发现推送出去的提交有问题，用 `revert` 生成一个反向提交，而不是抹掉它。
3. **不在网页上直接改代码后不拉取**。GitHub 网页上改过文件，本地必须先 `git pull` 再继续，否则下一次推送必然被拒，处理不当就会强推覆盖。

## 七、回溯：让仓库回到任何一个过去

### 7.1 五个层次先分清

回溯失败的绝大多数原因，是搞错了改动在哪一层。Git 里的一次改动会依次经过五个位置，越往后越"重"，撤销手段完全不同。

| 层次 | 改动在哪 | 撤销手段 | 危险度 |
|------|----------|----------|--------|
| 工作区 | 改了文件但没 `add` | `git restore 文件` | 低，丢弃未保存改动 |
| 暂存区 | 已 `add` 但没 `commit` | `git restore --staged 文件` | 低，改动仍在工作区 |
| 本地提交 | 已 `commit` 但没 `push` | `git reset` | 中，选错模式会丢代码 |
| 远端提交 | 已 `push` | `git revert` | 低，生成反向提交 |
| 发布版本 | 已打标签或归档 | 切回标签查看，不动历史 | 无 |

### 7.2 决策表：我想做什么

先查这张表，再执行命令。表格按"想达到的结果"组织，不按命令组织。

| 我的目标 | 命令 | 说明 |
|----------|------|------|
| 丢弃某个文件未提交的改动 | `git restore src/views/Home.vue` | 改动直接消失，无法恢复 |
| 撤销 `add`，但保留文件改动 | `git restore --staged 文件` | 常用，误 `add` 后第一反应 |
| 撤销最近一次提交，改动留在工作区 | `git reset --soft HEAD~1` | 想改提交信息或重新拆分提交时用 |
| 撤销最近一次提交，改动变成未暂存 | `git reset HEAD~1` | 默认模式，最常用 |
| 撤销最近三次提交并丢弃所有改动 | `git reset --hard HEAD~3` | 危险，先确认没有要保留的改动 |
| 撤销已经推送的某次提交 | `git revert 提交号` | 生成新提交，历史保留，可安全推送 |
| 撤销一次合并 | `git revert -m 1 合并提交号` | `-m 1` 表示保留主干一侧 |
| 把整个仓库退回某个标签 | `git switch --detach m3` | 只读查看，不动现有历史 |
| 把主干真正退回到某个标签 | `git reset --hard m3` 后强推 | 最后手段，能不用就不用 |
| 找回被 `reset --hard` 丢掉的提交 | `git reflog` 加 `git reset --hard HEAD@{n}` | 见 7.6 节，几乎总能救回 |
| 找回某个文件在旧版本的内容 | `git show m3:src/core/rules/drying.js` | 只读输出，重定向到文件即可另存 |

### 7.3 未提交的改动怎么撤

只想放弃改动：`git restore 文件名`，多个文件用 `git restore src/`。这一步不可撤销，因为改动从未被 Git 记录过，`reflog` 也救不回来，执行前用 `git diff` 看清楚。

写到一半但要切去修别的问题：用暂存挂起，而不是提交一个半成品。

```
git stash push -m "返潮规则写到一半"
git stash list                 确认挂起来了
git switch -c fix/cache-bug    去处理别的事
git switch main
git stash pop                  回来继续，内容原样恢复
```

`stash` 是本项目里被低估的工具：它让"临时切换任务"不再需要一次无意义的提交，也不需要冒险丢弃进度。

### 7.4 已提交未推送怎么撤

三种 `reset` 模式的区别只在于"改动被丢到哪一层"，命令本身结构一样。

| 模式 | 提交记录 | 暂存区 | 工作区 | 适用场景 |
|------|----------|--------|--------|----------|
| `--soft` | 撤销 | 保留 | 保留 | 想重新组织提交，改动全部还在且已暂存 |
| `--mixed`（默认） | 撤销 | 清空 | 保留 | 想重新挑选哪些文件进提交 |
| `--hard` | 撤销 | 清空 | 清空 | 确定这些改动全部不要了 |

判断口诀：`--soft` 是"提交没了，东西都在"；`--hard` 是"提交和东西都没了"；默认介于两者之间，东西在但没暂存。

`--hard` 之前先看一眼 `git status` 有没有未提交的改动——`--hard` 会连未提交的改动一起清掉，而这些改动不在任何提交里，只能靠编辑器撤销历史救。

### 7.5 已推送怎么撤

已推送的提交不能删，只能反向抵消。做法是 `revert`：它生成一个新提交，内容是原提交的逆操作，历史完整保留，也不需要强推。

```
git log --oneline -5              找到要撤的提交号，例如 a3f9c21
git revert a3f9c21                生成反向提交，编辑提交信息后保存
git push                          正常推送即可
```

撤一次合并要指定保留哪一侧，`-m 1` 指主干：

```
git revert -m 1 7b2e4d1
```

`revert` 之后如果再想把被撤掉的功能加回来，不能直接 `revert` 那个反向提交，需要先 revert 反向提交再加上原始改动，否则 Git 认为"已经撤过了"。这个坑遇到时按 7.6 节的思路处理，先看 `git log` 确认历史形状再操作。

### 7.6 reflog：最后一道保险

`reflog` 记录本地仓库每一次 HEAD 移动，包括提交、切换、重置、变基、合并。它默认保留 90 天，是"以为代码没了"时最先该用的命令。

```
git reflog                        列出最近所有 HEAD 变动
git reset --hard HEAD@{3}         回到三步之前的状态
git branch rescue HEAD@{5}        不确定时先建一个分支把那个状态固定下来
```

正确姿势是先建分支再决定，不要直接对着 `HEAD@{n}` 做 `--hard`。建了分支就有了一个不动的引用，怎么试都不怕。

典型事故与恢复：执行 `git reset --hard HEAD~5` 后发现丢了两天的活。此时 `git reflog` 会显示 `HEAD@{1}` 就是 reset 之前的位置，`git reset --hard HEAD@{1}` 即完整恢复，包括那些提交。

### 7.7 找回单个文件或单段代码

只要文件进过仓库，任何时候的内容都取得到。

```
git log --oneline -- src/core/rules/drying.js     看这个文件的历史
git log --diff-filter=D --oneline -- 文件路径      找它是哪次提交被删的
git show m3:src/core/rules/drying.js > drying.old.js   导出旧版本
git checkout HEAD~3 -- 文件路径                    把旧版本直接恢复到工作区
```

第三个命令里的 `m3` 是标签名，也可以换成任意提交号。结题写报告时需要引用"当时那一版权重配置是多少"，用的就是这条。

想查某段代码是哪次、为什么加进来的，用 `git log -S` 按内容搜索：

```
git log -S "dewPoint" --oneline -- src/core/utils/
```

它会列出所有让 "dewPoint" 出现次数发生变化的提交，比逐个翻 diff 快得多。

### 7.8 演示与回溯：拿旧版本给别人看

中期检查或答辩需要展示某个历史状态时，不要在当前工作区切来切去，用 `worktree` 把旧版本单独摊到一个目录里。

```
git worktree add ../demo-v0.5 v0.5
cd ../demo-v0.5 && npm install && npm run dev
```

这样旧版本跑在另一个端口上，当前工作区完全不受影响，演示完删掉目录并 `git worktree remove` 即可。没有 `worktree` 也可以直接用 `git archive` 导出压缩包，见 8.2 节。

### 7.9 三个月后怎么证明"这是我做的"

需要举证时，这四条命令比任何总结都有力。

```
git shortlog -sn --all                             提交总数与作者
git log --pretty=format:"%ad %s" --date=short       按日期列出所有提交
git tag -n                                         列出里程碑与说明
git diff --stat v0.1 v1.0                          首尾版本之间的改动规模
```

`git log --since=2026-11-01 --until=2027-03-01` 可以按学期切出阶段记录，直接对应中期检查的时间区间。

## 八、备份与容灾

### 8.1 三个副本

同一份代码至少存在三个独立位置，缺一不可：本机工作目录、远端仓库、离线归档（移动硬盘或学校网盘）。前两个解决日常丢失，第三个解决账号或平台层面的事故，例如仓库误删、账号不可用、误设为公开后删除重来。

### 8.2 每学期末归档

每个学期结束、以及每个里程碑完成后，导出一份完整的压缩包，文件名带日期和版本。

```
git archive --format=zip --output=archives/decision-assistant-v0.5-20270430.zip v0.5
```

`git archive` 只打包被 Git 跟踪的文件，自动排除 `node_modules` 和临时文件，比直接压缩文件夹干净。压缩包连同当期的回测数据、演示视频一起放到移动硬盘，并在 `docs/progress/log.md` 记一行"归档于何时、放在哪里"。

### 8.3 中断后怎么接上

生病、考试周、换电脑之后恢复工作，按下面四步走，不依赖记忆。

1. 新机器装好 Git 与 Node，配好用户名邮箱与 SSH 密钥；
2. `git clone` 仓库，`npm install` 装依赖；
3. 打开 `docs/progress/log.md` 看最后一次记录：做完了什么、下一步做什么、卡在哪里；
4. 打开 `CHANGELOG.md` 与最近的标签，确认当前处于哪个里程碑，然后用 `git log --oneline -10` 对齐上下文。

这四步能成立的前提是：周志真的在写，标签真的在打。这也是本文件反复强调这两件事的原因——它们不是形式，是给未来的自己留的说明书。

### 8.4 密钥泄露的处理

发现密钥进了仓库，动作顺序不能错：先去平台后台**作废并重新生成**密钥，再处理仓库。反过来做没有意义，因为历史里的密钥已经泄露。

处理仓库时，如果密钥所在提交还没推送，用 `reset` 或 `revert` 撤掉即可；如果已经推送且仓库是私有的，改配置并把密钥移入 `.env`（已由 `.gitignore` 排除），在 `docs/decisions/` 记一条说明，不必为了抹掉历史而重写整个仓库。本项目唯一可能涉及的密钥是天气接口的 key，免费额度本身不敏感，但仍按此流程处理。

### 9.1 周志

`docs/progress/log.md` 每周日追加一段，五句话以内，不写感想只写事实。

```
## 2026-11-08
```

这份文件是中期检查与结题报告里"项目过程"章节的原料，也是自己中断后恢复上下文的唯一依据。按周写，别攒到月底补，补出来的内容一定是编的。

### 9.2 CHANGELOG

`CHANGELOG.md` 按版本倒序记录，每个版本三到五条，与标签一一对应。

```
## v0.5 - 2027-04-28
- 新增返潮预警、出行带伞、穿衣体感三类指数

```

结题报告的"研究成果"部分可以直接从这份文件整理，不需要重新回忆。

### 9.3 结题时从仓库产出的四份材料

| 材料 | 生成方式 | 用途 |
|------|----------|------|
| 开发过程时间线 | `git log --pretty=format:"%ad %s" --date=short` 整理成表 | 报告"项目过程"章节 |
| 里程碑记录 | `git tag -n` 输出 | 报告"进度安排完成情况" |
| 版本差异统计 | `git diff --stat v0.1 v1.0` | 说明工作量与规模 |
| 关键决策依据 | `docs/decisions/` 汇总 | 答辩时回答"为什么这么做" |

这四份材料加起来不到一小时就能整理完，前提是前面十个月认真提交。这也是本文件最实际的价值：把结题时最耗时的"过程材料"分摊到每一天的两分钟里。

### 9.4 截图与视频要标版本

`docs/progress/` 下的截图文件名带日期与标签，例如 `20270428-m5-首页.png`。演示视频在片头注明版本号，并在 `CHANGELOG` 里记录"演示视频对应 v0.5"。否则三个月后无法确认某段视频对应哪版界面，答辩时说不清"现在演示的和报告里的为什么不一样"。

## 十一、常见错误速查

| 现象 | 原因 | 处理 |
|------|------|------|
| 推送被拒，提示 non-fast-forward | 远端有本地没有的提交 | `git pull --rebase` 后重推 |
| 提交里混进了 `node_modules` | 用了 `git add .` 且 `.gitignore` 未覆盖 | `git rm -r --cached node_modules` 后重新提交 |
| 整个文件被标记为改动 | 换行符或编码变化 | 配 `.gitattributes`，必要时 `git add --renormalize .` |
| 提示 detached HEAD | 直接切到了标签或提交号 | 要在此处改动就 `git switch -c 新分支名` |
| 想撤的提交已经推送 | 不能删只能反向 | 用 `git revert`，见 7.5 |
| `reset --hard` 后代码不见了 | 工作区被清空 | `git reflog` 找回，见 7.6 |
| 拉取后出现大量冲突 | 本地与远端改了同一处很久没同步 | 先 `git merge --abort`，改为逐文件合并，或保留一侧重做 |
| 网页上改过文件，之后推不上去 | 本地历史落后 | 先拉取，冲突按 6.3 处理 |
| 提交信息写错但已推送 | 已推历史不宜改写 | 保留错误提交，用 `revert` 或在下一次提交说明中更正 |
| 压缩包里有几十兆的临时文件 | 直接压缩了文件夹而非 `git archive` | 改用 `git archive` |

## 十二、命令速查

按使用频率排列，前六条覆盖日常九成操作。

```

```

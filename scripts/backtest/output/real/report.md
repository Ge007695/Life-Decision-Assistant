## 二、判定口径

- 预测为正：`drying` 结论 `level == 4`（适宜）
- 实际为正：**次日干燥**，即次日降水合计 = 0 且次日平均相对湿度 ≤ 85%
- 误判（FP）：判「适宜」但次日降水 > 0 或次日平均湿度 > 85%（工作指导书 11.3 的原话）
- 漏判（FN）：判「不适宜」但次日其实干燥——代价是保守，不算错得离谱，但会降低可用性

准确率 = (TP+TN)/N；精确率 = TP/(TP+FP)；召回率 = TP/(TP+FN)。

## 六、拟合权重是怎么来的

- 方法：在权重单纯形上做网格搜索，步长 0.05，共评估 **3876** 组合，覆盖 729 天样本；
- 约束：每项权重 ≥ 0.05。无此约束时搜索会落到「降水概率 0.80、温度 0、日照 0」这类解，但 `createConfig()` 规定权重必须为正数，那样的解无法写回 `indices.json`，也就无法在页面上复现；
- 目标：准确率最高；平局依次比误判数更少、与经验权重更接近，保证结果可复现；
- 实现：纯标准库枚举，未使用 numpy / pandas（本机 Python 环境未装科学计算包）。

> 注意：在同一批数据上选权重、再用同一批数据评准确率，属于**样本内评估**，拟合方案的准确率天然偏高，不能直接说「比经验权重好」。严谨做法是切成训练段/验证段或做时间序列交叉验证，这一项列在待办里。

## 七、口径与已知问题

- hourly 用的是**当日 0—23 时**，而线上 `weather.js` 给的是**从当前小时起的未来 48 小时**；因此回测里的「最佳时段」只在当天范围内找，与线上口径不完全一致，改进方式是把 hourly 换成「当日 09:00 起连续 24 小时」。
- 归档接口没有 `precipitation_probability`，本回测用小时降水量与当日累计降水构造代理值（≥1mm→100，≥0.3mm→85，>0→65，其余按当日累计 45/25/15/5）。降水概率在权重里占 0.25，代理值会系统性影响分数，真实数据接入后应重新评估。
- `damp`（返潮）规则 v1.0.0 已接入，本次 0/729 条返回降级结论；返潮没有可用的实测标注，故只做描述性统计，不评准确率。
- `engine.js` 的 `nowIso()` 在 `config.checkedAt` 存在时忽略注入时钟，所以 CSV 里没有收录 `updatedAt`——它记录的是跑脚本的墙上时间，不是历史日期。
- 判定「实际为干燥」用的是次日 24 小时合计降水与平均湿度，「今天晾、次日收」这个时间差在工作指导书里没有更细的口径，本脚本按字面实现。

## 八、结论（当前仅限脚本层面）

1. Python → `run_rule.js` → `engine.run()` 的链路可跑通，回测与线上共用同一份规则代码；
2. 逐日构造入参、批量调用、CSV 落盘、混淆矩阵与按月统计均已实现；
3. 表中数字为**示例数据结果**，真实准确率待接入实测数据后重跑；
4. `damp`（返潮）只做描述性统计：缺少「是否真的返潮」的实测标注，没有标注就没有准确率可言，宁可空着也不编一个数字。
